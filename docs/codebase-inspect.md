## 목적과 범위

레포 전체의 유지보수를 점검한다. 이번 단계는 조사와 결과 정리까지다. 코드·테스트·주석·설정을 수정하거나 삭제하지 않고 커밋하지 않는다. 조사 결과만 `.scratch/maintenance-audit/` 아래에 작성한다. `.scratch`는 `link-worktree-files.sh`가 기준 체크아웃으로 링크해 두므로 어느 워크트리에서 조사해도 같은 자리에 쌓인다.

대상은 루트 문서·설정·스크립트, `docs/`, `src/`다. `node_modules`, `.next`, `pnpm-lock.yaml`은 제외한다. `docs/reference/`는 외부 원문을 옮겨 둔 읽을거리라 내부 품질 점검 대상에서 빼고, 화면·`docs/fact-check-log.md`와 어긋나는 인용만 확인한다. 로컬 환경 파일(`.env*`)은 열지 않는다.

## 판단 기준

루트 `AGENTS.md`를 먼저 읽고, 거기서 가리키는 정본을 따라간다.

| 범위                    | 적용 기준                                                           |
| ----------------------- | ------------------------------------------------------------------- |
| 코드 규약·아키텍처      | `CLAUDE.md`                                                         |
| 용어                    | `CONTEXT.md`                                                        |
| 모델·구조 판단과 근거   | `docs/adr/`                                                         |
| 수치·연도·규격          | `docs/fact-check-log.md`                                            |
| 명령어                  | `package.json`의 `scripts`                                          |
| 워크트리 포트·공유 파일 | `scripts/worktree-ports.mjs`, `link-worktree-files.sh`의 `ITEMS`    |
| 린트로 강제되는 규약    | `eslint.config.mjs`. 룰을 끈 이유가 주석에 있으므로 함께 읽는다     |
| vendored UI             | `src/components/ui/`. 린트 제외 대상이고, 원본과 다른 점은 ADR 0010 |

문서도 오래됐을 수 있다. 코드와 문서가 다르면 정본의 의도, 기존 동작, 관련 테스트·결정 기록을 대조해 어느 쪽을 고쳐야 하는지 근거를 제시한다.

| 분류                | 기준                                                                   | 필요한 증거                                    |
| ------------------- | ---------------------------------------------------------------------- | ---------------------------------------------- |
| P1 실제 오류        | 동작이 틀리거나, 화면의 수치가 틀리거나, 검증 명령이 실패하는 것       | 재현 절차 또는 실패 명령, 기대 결과, 실제 결과 |
| P2 명시된 규약 위반 | `CLAUDE.md`·`CONTEXT.md`·ADR·`eslint.config.mjs` 주석에 쓰인 규칙 위반 | 정본의 파일·위치와 해당 규칙                   |
| P3 개선 제안        | 규칙에 없지만 유지보수에 도움이 되는 것                                | 구체적인 유지보수 비용, 개선 효과, 변경 위험   |

개인 취향에 따른 변경을 P1·P2로 올리지 않는다. 환경 문제(네트워크, API 키 부재, 외부 API 장애)로 검증이 실패한 경우 코드 오류와 분리한다. 조사 범위를 채우기 위해 문제를 만들어내지 않고, 발견 없음과 미검증을 구분한다.

## 조사 순서와 역할 분담

1. 시작 전에 Git 상태와 기준 커밋을 기록하고 기존 사용자 변경을 보존한다.
2. 적용할 정본을 읽고 조사 대상·제외 대상을 목록화한다. 영역별 대상 파일 목록, 점검 방식, 조사 상태를 기록한다.
3. 다음 다섯 영역을 서브에이전트에 나눠 조사한다. 동시 실행 한도에 맞춰 순차 배정해도 된다.
4. 부모 에이전트는 교차 영역과 검증 실행을 조율하고, 결과를 합칠 때 중복과 오탐을 직접 확인한다.
5. 결과 파일을 작성하고 Git 상태를 시작 시점과 비교한다.

| 담당 영역      | 범위                                                                                                                                                                                                                                   |
| -------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 문서           | `AGENTS.md`·`CLAUDE.md`·`CONTEXT.md`, `docs/adr/`, `docs/agents/`, `docs/fact-check-log.md`, `docs/codebase-inspect.md` 자신, `docs/reference/` 인용 대조                                                                              |
| 데이터 계층    | `src/app/api/`, `src/lib/loaders/`, `src/lib/cache*.ts`·`fred.ts`·`yahoo.ts`·`series.ts`·`prefetch.ts`, `src/hooks/use-*.ts` 중 데이터 훅                                                                                              |
| 모델           | `src/lib/*-models.ts`·`*-concept.ts`·`bcra.ts`·`address-types.ts`, `src/app/<page>/models.ts`                                                                                                                                          |
| 화면           | `src/app/**`의 페이지·컴포넌트, `src/components/`(`ui/` 제외), 차트·재생 훅(`use-chart.ts`·`use-round-engine.ts` 등)                                                                                                                   |
| 루트 실행 환경 | `package.json`, `pnpm-workspace.yaml`, `next.config.ts`, `tsconfig.json`, `eslint.config.mjs`, `components.json`, `postcss.config.mjs`, `.nvmrc`, `.gitignore`, 포맷 설정, `.husky/`, `scripts/`, `link-worktree-files.sh`, `.vscode/` |

각 서브에이전트는 담당 영역에 해당하는 한 아래 「조사 항목」의 모든 항목을 점검한다. 실제 오류와 명시된 규약 위반을 먼저 보고, 나머지 항목은 표본 조사가 되면 그 범위를 기록한다.

「외부 API와 캐시」는 데이터 계층 담당이, 「수치와 규제 값」은 모델 담당이, 「화면 규약」·「shadcn primitive 미사용」·「접근성과 화면 상태」는 화면 담당이 본다. 「의존성」과 「보안 취약점」의 의존성 항목은 루트 실행 환경 담당이 본다. 「API 키와 민감 정보」와 「보안 취약점」의 입력 처리는 데이터 계층 담당이, 응답 헤더(`next.config.ts`)는 루트 실행 환경 담당이 본다. 레지스트리에 접속하는 `pnpm deps:check`·`pnpm run audit`는 부모 에이전트가 「의존성 점검」대로 한 번만 실행해 결과를 나눠 준다.

파일별로 직접 읽음·정적 검색·미점검을 구분한다. 일부만 읽은 파일은 읽은 구간을 기록한다. 정적 검색은 사용한 패턴과 범위를 남긴다. 표본 조사한 부분을 전수 확인한 것으로 표현하지 않는다. `SimTabs`·`ExplainCard`는 접힌 내용을 DOM에 두지 않으므로 무엇이 쓰였는지는 소스로 센다.

부모 에이전트가 직접 확인할 교차 영역은 다음과 같다.

- `cache-config.ts`의 `ENDPOINTS` 키, `src/app/api/<key>/` 디렉터리, `useEndpoint<T>(key)` 호출이 한 벌로 맞는지
- 라우트의 응답 타입과 훅의 제네릭 타입이 같은 정의를 가리키는지(예: `StocksData`와 `stocks` 라우트)
- 같은 모델·수치를 페이지와 `src/lib/`가 따로 갖고 있어 함께 고쳐야 하는지
- `src/lib/nav.ts`의 페이지 목록과 `src/app/` 아래 실제 라우트, 사이드바 그룹과 페이지 부류(대시보드·설명형)가 맞는지
- 화면 문구·코드 식별자·`CONTEXT.md` 사이의 용어 대응과 의미 차이

기존 이슈·ADR·규약의 예외와 대조해 의도된 동작과 알려진 문제를 구분한다. 같은 문제가 이미 기록되어 있으면 기존 기록을 연결하고 새 티켓을 중복 생성하지 않는다. `.scratch/maintenance-audit/issues/`에 티켓이 하나라도 있으면 기존 조사로 보고 근거를 재검증해 갱신하며, 기존 티켓 번호와 사용자 기록을 보존한다. 티켓이 없으면 `report.md`가 있더라도 새 조사로 보고 덮어쓴다.

## 조사 항목

### 문서

- 실제 코드·명령어·경로와의 불일치. `CLAUDE.md`가 이름으로 가리키는 파일·함수·상수(`REGULATION`, `acquisitionTaxRate`, `RAINBOW_BANDS`, `setupRef` 등)가 실재하는지
- `CLAUDE.md`가 적은 개수·목록(대시보드 다섯, `*-concept.ts` 아홉, 야후를 읽는 라우트 넷, `simulation.tsx`의 프리미티브 목록)이 현재 코드와 맞는지
- 깨진 링크, 중복되거나 상충하는 설명. ADR끼리, ADR과 `CLAUDE.md` 사이의 충돌
- 문서에 적힌 실행 방법과 현재 설정의 차이
- `docs/fact-check-log.md`의 「시간이 지나면 다시 봐야 하는 값」 중 대조 시점이 오래된 항목

### 설정 파일

설정이 현재 코드·문서·실행 경로와 맞는지 점검한다.

| 파일                                                     | 볼 것                                                                            |
| -------------------------------------------------------- | -------------------------------------------------------------------------------- |
| `package.json`                                           | scripts가 문서의 명령어 목록과 맞는지, `lint-staged` 패턴                        |
| `pnpm-workspace.yaml`                                    | `allowBuilds`·`overrides`·`minimumReleaseAgeExclude`가 아직 필요한지             |
| `next.config.ts`, `tsconfig.json`, `postcss.config.mjs`  | 경로 별칭·옵션이 실재하는 경로와 현재 도구 버전에 맞는지                         |
| `eslint.config.mjs`                                      | 끈 룰의 근거 주석이 지금도 맞는지(주석의 건수·파일 목록), 파일별 예외가 필요한지 |
| `.prettierrc`·`.prettierignore`, `.vscode/settings.json` | Tailwind 진입점·클래스 함수 목록이 서로, 그리고 `eslint.config.mjs`와 같은지     |
| `components.json`                                        | 별칭·경로가 실재하는지                                                           |
| `.husky/pre-commit`, `.nvmrc`, `.gitignore`              | 가리키는 대상이 실재하는지, `.nvmrc`와 문서의 셋업 안내가 같은 버전인지          |
| `scripts/*.mjs`, `link-worktree-files.sh`                | `CLAUDE.md`「워크트리와 로컬 설정」의 설명과 동작이 같은지                       |

- 설정이 가리키는 경로·파일·스크립트·패키지가 실재하는지 확인한다. ignore 패턴, `files` 글롭, `entryPoint`, `extends` 대상이 여기에 든다.
- 효력이 없는 설정을 찾는다. 없어진 파일을 대상으로 한 룰 예외, 지워진 경로의 ignore 패턴, 현재 도구 버전이 지원하지 않는 옵션, 기본값과 같은 값을 다시 적은 항목이 해당된다.
- 코드의 `process.env.*` 참조와 `CLAUDE.md`「환경변수」 표를 대조한다. 키 이름은 코드 참조로만 확인하고 환경 파일을 열지 않으며 값은 보고서에 복사하지 않는다.

검증 명령이 실패하면 P1, 규약 문서와 다르면 P2, 나머지는 P3다.

### 코드와 아키텍처

- 유사 기능 사이의 구현·타입·오류 처리·네이밍 불일치. 라우트끼리, 데이터 훅끼리, 차트 컴포넌트끼리 비교한다
- `CLAUDE.md`「아키텍처」의 경계 위반: 컴포넌트가 훅을 거치지 않고 `/api`를 부르는 곳, lightweight-charts를 `use-chart.ts` 밖에서 직접 import하는 곳, 라우트 밖에서 외부 도메인을 부르는 곳
- 「설명 페이지의 모델 배치」 기준과 다른 새 모델 위치. 기존 파일은 옮기지 않기로 했으므로 그 규칙 이후에 생긴 것만 본다
- 같은 책임이나 지식이 여러 곳에 있어 함께 수정해야 하는 코드·문서

모양이 비슷하다는 이유만으로 추상화를 제안하지 않는다. 함께 변경되어야 하는 책임인지 판단하고, 규약이나 ADR이 의도적으로 허용한 복제는 구분한다.

### 불필요한 추상화

행위를 더하지 않는 간접 계층을 찾는다. 판단 기준은 그 계층을 인라인했을 때 읽어야 할 파일·심볼이 줄고 동작이 같은가다.

후보:

- 통과용 re-export 파일
- 호출처가 하나뿐인 함수·훅·컴포넌트 래퍼 중 이름을 바꾸는 것 외에 하는 일이 없는 것
- 인스턴스가 하나뿐인 제네릭·팩토리·설정 객체
- 상태·컨텍스트 없이 자식만 돌려주는 Provider·HOC
- 옵션 인자를 받지만 모든 호출처가 같은 값을 넘기는 함수
- 구현이 하나뿐이고 교체 지점도 아닌 인터페이스·타입 별칭

제거 대상이 아닌 것:

- 규약이 정한 경계. `use-*.ts`의 `useEndpoint` 한 줄 래퍼는 "컴포넌트는 훅을 통해서만 데이터 접근" 규약의 경계다. `use-chart.ts`의 lightweight-charts 재수출도 같다.
- 단일 출처로 둔 것. `ENDPOINTS`, `NAV_GROUPS`, `REGULATION`, `src/lib/utils.ts`의 표기 함수는 호출처가 하나여도 출처를 하나로 모으려는 자리다.
- 재생 배선 셋(`useRoundEngine`·`useTrajectory`·`useTrajectoryPlayer`). 고르는 기준이 `CLAUDE.md`에 있다.
- 서버·클라이언트 경계 때문에 둔 간접 계층. 라우트가 API 키와 외부 도메인을 숨기는 프록시 역할이 그 예다.

후보마다 인라인했을 때 사라지는 파일·심볼, 호출처 수, 보존해야 할 동작을 적는다. 규약 위반이면 P2, 그 외는 P3다. 제거는 후속 수정 단계에서 한다.

### 용어 통일성

- `CONTEXT.md`의 정의와 화면 문구·코드 식별자·타입·문서의 용어가 일치하는지 확인한다. 「피할 말」로 적힌 표현이 화면에 남았는지 본다.
- 같은 개념을 서로 다른 이름으로 부르거나 다른 개념을 같은 이름으로 부르는지 확인한다. `CLAUDE.md`「같은 화면의 두 숫자」 규칙도 여기서 본다.
- 한글·영문 명칭과 약어의 대응이 일관적인지 확인한다.
- 새로 등장한 도메인 개념이 용어집에 누락되어 있는지 확인한다.
- 외부 데이터 제공처의 명칭이나 업계 표준 약어 때문에 필요한 차이는 구분하고 기계적으로 통일하지 않는다.

각 불일치에는 개념, 정본 용어, 실제 사용 표현, 사용 위치, 권장 대응을 적는다.

### 미사용 요소

코드, export, 파일, 패키지 의존성, 설정, 스크립트, 참조를 조사한다. 단순 검색 결과만으로 dead code를 확정하지 않고 다음을 확인한다.

- Next.js 파일 기반 진입점: `page`·`layout`·`route`·`loading`·`error`·`manifest`·`icon` 등
- 동적 import, `src/lib/prefetch.ts`처럼 키 문자열로 간접 참조하는 곳
- `package.json` scripts, 설정 파일, `link-worktree-files.sh`에서의 참조
- `src/components/ui/`는 shadcn이 한꺼번에 들여온 파일이라 안 쓰는 export가 있어도 문제로 잡지 않는다. 파일 단위로 한 번도 import되지 않는 컴포넌트만 후보로 둔다
- `cache-config.ts`의 `ENDPOINTS`에 있는데 라우트나 훅이 없는 키, 그 반대

런타임 참조 가능성을 배제할 수 없으면 확정하지 않고 후보로 남긴다. 미사용 의존성은 수동 판정만 하고 확신도를 낮게 적는다. knip 등 도구 도입이 필요하면 제안 항목으로 분리하고 이번 조사에서 도입하지 않는다.

### 의존성

`package.json`의 의존성 목록이 최신인지 조사한다. 명령과 실행 주체는 「의존성 점검」이 정하고, 결과 분류는 여기서 한다.

- `pnpm deps:check`(`pnpm -r outdated`) 결과를 패키지·현재·최신으로 표로 정리하고 patch·minor·major로 나눈다. major는 마이그레이션 가이드 유무와 예상 영향을 적는다.
- 버전을 고정한 것(`next`·`react`·`react-dom`·`eslint-config-next`)과 범위로 둔 것이 섞여 있다. 고정한 쌍이 서로 맞는지(`next`와 `eslint-config-next`) 확인한다.
- `pnpm-workspace.yaml`의 `overrides`(`postcss`)와 `minimumReleaseAgeExclude`가 아직 필요한지 확인한다. `pnpm why <pkg>`로 전이 의존 경로를 추적하고, 각 소비 패키지의 원래 요구 범위까지 확인한 뒤 필요성을 판단한다. 직접 의존성이 안전한 버전이어도 전이 의존성에는 구버전이 남을 수 있으므로 직접 의존성 버전만으로 제거를 제안하지 않는다.
- `.nvmrc`와 `@types/node`의 major가 맞는지 확인한다.
- 미사용 의존성은 「미사용 요소」의 기준을 따른다.

갱신은 이번 단계에서 하지 않는다. 수정 묶음에 의존성 갱신을 따로 두고 patch·minor·major로 나눠 변경 위험을 적는다.

### 테스트 코드

이 레포의 테스트는 두 벌이다. `scripts/*.test.mjs`는 `node:test`(`pnpm test:scripts`)로, `src/**/*.test.ts`는 Vitest(`pnpm test`, 설정은 `vitest.config.ts`)로 돈다. Vitest 쪽은 순수 계산 모델과 표기 함수의 회귀 테스트이고 node 환경이라 화면(DOM)은 띄우지 않는다. E2E는 없다.

- 기존 테스트: 대상 스크립트의 현재 동작과 맞는지, 항상 성공하는 단언이나 방치된 `skip`·`todo`가 있는지
- 테스트 공백: 순수 계산 모델(`src/lib/*-models.ts`·`*-concept.ts`, `src/app/<page>/models.ts`)과 `src/lib/utils.ts`의 표기 함수 중 테스트 파일이 없거나, 틀리면 화면 수치가 조용히 틀리는데 단언이 없는 것. `docs/fact-check-log.md`에 대조 결과가 있는데 테스트로 옮기지 않은 값도 공백이다. 화면 파일(`.tsx`) 안에만 있는 계산은 모델로 옮겨야 테스트할 수 있다

새 테스트는 제안으로만 남긴다. 테스트 러너는 위 두 벌로 정해져 있으니 새 도구가 필요한 제안은 별도 항목으로 분리한다.

### 외부 API와 캐시

`CLAUDE.md`「데이터 흐름」과 「환경변수」가 정본이다.

- 키 대응: `ENDPOINTS` 키 = `/api/<key>` 경로 = `useEndpoint<T>(key)` 인자. 셋 중 하나만 있는 것을 찾는다.
- 신선도: 라우트가 TTL·`staleTime`·`refetchInterval`을 `cache-config.ts` 밖에서 따로 정하는 곳이 있는지 본다.
- 캐시 경유: 모든 라우트가 `cached(key, fetcher)`를 거치는지, 라우트의 캐시 키가 `ENDPOINTS` 키와 같은지 본다.
- 키 부재 분기: `FRED_API_KEY`·`ECOS_API_KEY`를 읽는 라우트가 모두 키가 없을 때 500이 아니라 `available: false`를 돌려주고, 화면이 그 분기를 그리는지 확인한다.
- 실패 전파: 심볼 하나가 죽으면 라우트 전체가 실패하는 `Promise.all` 경로(`src/lib/yahoo.ts`·`src/lib/fred.ts`)와 라우트의 `SYMBOLS`·화면 표가 한 벌인지 확인한다. 야후 티커가 살아 있는지는 네트워크 확인이라 외부 확인 후보로 둔다.
- 응답 모양: 라우트가 돌려주는 타입과 훅의 제네릭이 같은 정의인지, 캐시에 남은 옛 응답 형태가 새 코드를 깨뜨릴 수 있는 변경이 있었는지(캐시 키에 환경·버전 구분이 없다) 본다.
- 스탬피드 차단: `src/lib/cache.ts`의 락 획득·해제·타임아웃 경로에서 fetcher 실패 시 락이 남는지 본다.

화면이 틀리거나 라우트가 실패하면 P1, `CLAUDE.md`의 분기·대응 규약을 어기면 P2, 나머지는 P3다. 이번 단계에서 외부 API를 호출하지 않는다.

### shadcn primitive 미사용

`src/components/ui/`의 primitive나 `src/components/simulation.tsx`의 공용 프리미티브가 맡을 일을 소비처가 원시 요소나 손으로 짠 로직으로 처리하는 자리를 찾는다. primitive를 쓰면 포커스·키보드·aria 배선과 `variant`·`size` 계약을 한곳이 갖는다. `shadcn/no-restyle`은 primitive를 덮어쓴 자리만 잡고 primitive를 아예 쓰지 않은 자리는 잡지 못하므로 직접 찾는다.

후보:

- 스타일을 직접 입힌 원시 요소: `<button>`·`<input>`·`<select>`·`<hr>`. 대응 primitive는 `Button`·`Input`·`Select`·`Separator`다.
- 손으로 짠 상호작용: 바깥 클릭·ESC·포커스 가두기를 직접 처리하는 드롭다운·팝오버·드로어, `title` 속성으로 대신한 툴팁, 직접 만든 탭·접기. `DropdownMenu`·`Drawer`·`Tooltip`·`Tabs`·`Collapsible`이 대응한다.
- 모양만 흉내 낸 요소: 배지처럼 꾸민 `span`, `animate-pulse` 자리표시. `Badge`·`Skeleton`이 대응한다.
- `simulation.tsx`의 프리미티브(`SimTabs`·`ControlSlider`·`SegmentedControl`·`Metric`·`StatusBanner`·`MarkTable` 등)와 같은 것을 페이지가 다시 만든 자리. `ControlSlider`를 두고 `Slider`를 직접 쓰면 손끝 치수와 −/+ 버튼이 빠진다.
- 설치되지 않은 shadcn 컴포넌트가 맡을 일을 직접 만든 자리. 설치 목록은 `src/components/ui/`, 레지스트리는 `components.json`과 shadcn MCP로 확인한다. 새 primitive 추가는 제안으로만 남긴다.

제외 대상:

- `src/components/ui/*` 자체. primitive 내부의 원시 요소는 대상이 아니다.
- 설명형 페이지의 `Panel`. `Card` 대신 쓰는 것이 의도다(ADR 0010).
- SVG로 그린 도식·삽화와 차트 캔버스. primitive가 대응하지 않는다.
- 네이티브 요소가 곧 맞는 구현인 자리. 페이지 이동 링크(`next/link`), 스크롤 가능한 데이터 표의 `<table>` 같은 것이다. `Table` primitive가 설치되지 않았으므로 표는 설치 제안 후보로만 적는다.

후보마다 위치, 대응 primitive, 교체하면 달라지는 동작(포커스·키보드·aria·모양), 필요한 variant를 적는다. 맞는 variant가 없어 교체가 곧 덮어쓰기가 되는 자리는 `eslint.config.mjs`의 `no-restyle` 정책(컴포넌트는 자기 상자를, 호출부는 배치와 강조를 소유한다)에 따라 primitive 기본값을 고칠지, contract를 넓힐지 제안한다. 재현되는 접근성·기능 결함은 P1, 규약 위반은 P2, 나머지는 P3다. 교체는 후속 수정 단계에서 한다.

### 주석

- 코드와 어긋난 설명, 코드를 그대로 반복하는 주석
- 주석 처리된 죽은 코드, 유효기간이 지난 `TODO`·`FIXME`
- 주석이 적은 건수·목록이 지금 코드와 맞는지. 이 레포는 설정 주석에 숫자를 자주 적는다(`eslint.config.mjs`의 "33곳 중 31곳", "걸리는 4곳")

설계 이유, 외부 계약, 제공처별 함정(`CLAUDE.md`가 문서 대신 해당 파일 주석에 두기로 했다), 예외 처리의 배경을 설명하는 주석은 보존 대상으로 구분한다. 타입·린트·번들러 지시문은 일반 설명 주석과 구분한다.

`TODO`·`FIXME`는 관련 구현이나 이슈 상태를 확인할 수 없으면 오래됐다는 이유만으로 제거 대상으로 확정하지 않는다. 주석이 틀렸더라도 코드가 잘못된 것인지 먼저 확인하고, 제거와 설명 수정 중 적절한 대응을 제시한다.

### 코드의 이해 용이성

- 이름만으로 역할을 알기 어려운 식별자, 과도한 중첩·분기
- 숨은 부수 효과, 암묵적 실행 순서 의존. 간접 계층 자체는 「불필요한 추상화」가 다룬다
- 하나의 함수나 모듈을 이해하기 위해 여러 파일의 상태와 조건을 동시에 추적해야 하는 부분
- 도메인 의도가 자료구조나 기술적 처리에 가려진 부분. 시뮬레이션의 라운드·궤적 계산이 렌더 코드에 섞인 곳이 대표적이다
- 타입으로 표현할 수 있는 제약을 여러 조건문으로 반복하는 부분

개선 후보마다 이해를 어렵게 만드는 구체적인 이유, 읽어야 하는 흐름, 기존 동작을 보존하는 개선 방향을 적는다. 단순히 짧게 만들거나 함수를 더 나누는 것을 개선으로 간주하지 않는다. 분리·인라인화·명명 변경 등이 실제로 추적해야 할 개념과 파일 이동을 줄이는지 판단한다.

취향이나 익숙함의 차이는 문제로 확정하지 않는다. 명시된 규약 위반이나 실제 오류가 아니면 P3로 분류한다.

### 비동기 상태와 렌더 일관성

- 재생 중인 시뮬레이션에서 파라미터를 바꾸거나 탭을 옮길 때 타이머·애니메이션 프레임이 정리되는지, 낡은 궤적이 남는지 확인한다. 리마운트는 `key`로 한다는 규약을 따르는지 본다.
- 데이터 훅의 로딩·오류·`available: false` 상태를 화면이 구분해 그리는지 확인한다.
- 서버 HTML과 첫 클라이언트 렌더가 어긋나는 곳(JS로 중단점 판정, 렌더 중 `Date.now()`·`Math.random()`)을 찾는다. 커밋 03b0f31이 이 부류다.
- 실제 호출 흐름과 재현 근거 없이 잠재적 경쟁 상태를 P1로 확정하지 않는다.

### API 키와 민감 정보

로그인·권한이 없는 공개 사이트다. 지킬 것은 서버의 API 키와 캐시 저장소다.

- `FRED_API_KEY`·`ECOS_API_KEY`·`KV_*`가 라우트 밖(클라이언트 컴포넌트, `NEXT_PUBLIC_*`)으로 새는 경로가 없는지 확인한다.
- 라우트가 외부 API 오류를 그대로 돌려줄 때 요청 URL(쿼리의 API 키 포함)이 응답·로그에 실리는지 확인한다.
- 라우트가 쿼리 파라미터를 받아 외부 URL이나 캐시 키를 만드는 곳이 있으면, 임의 값으로 캐시를 채우거나 외부 호출을 늘릴 수 있는지 본다.
- 실제 비밀값은 보고서에 복사하지 않는다. 위치와 노출 경로만 기록한다.

### 보안 취약점

- 의존성 취약점: `pnpm run audit`(`pnpm audit --audit-level=high`) 결과를 패키지·심각도·의존 경로·수정 버전으로 정리한다. `pnpm-workspace.yaml`의 `overrides`가 이미 막은 것과 새로 나온 것을 나눈다. 수정 버전이 없는 건은 외부 확인 후보다.
- 응답 헤더: `next.config.ts`에 `headers()`·`poweredByHeader`가 없는 상태가 의도인지, Vercel 기본값으로 충분한지 판단한다. 추가는 강화 제안(P3)이다.
- 입력 처리: `dangerouslySetInnerHTML`, `eval`·`new Function`, 사용자 입력이나 외부 응답으로 만든 URL·`href`를 찾는다.

재현되는 취약점은 P1, 규약이나 주석이 정한 정책과 다르면 P2, 강화 제안은 P3다. 재현 절차는 남기되 공격에 쓰일 값은 적지 않는다.

### 접근성과 화면 상태

- 인터랙티브 컨트롤(슬라이더·세그먼트·재생 버튼·탭·드로어)의 키보드 조작, 라벨, 포커스 이동·복귀를 점검한다.
- `ControlSlider`의 치수·터치 규약(`CLAUDE.md` 표)을 다른 컨트롤이 깨뜨리지 않는지, 차트가 세로 스크롤을 먹지 않는지 코드로 확인한다.
- 로딩·빈 결과·오류·키 없음 상태에서 화면이 상황을 안내하는지 확인한다.
- 이번 단계는 코드 정적 점검으로 한정한다. dev 서버와 브라우저를 띄우지 않고, 그 사실을 기록한다. 브라우저 확인이 필요한 항목은 경로·상태·화면 크기(360px 모바일 포함)를 적어 추가 확인 후보로 남긴다.
- 재현되는 기능 장애는 P1, 명시된 규약 위반은 P2, 그 외 사용성 개선은 P3로 구분한다.

## 검증 실행

### 기본 검증

레포 루트에서 다음을 실행해 현재 검증 상태를 확보한다. `pnpm inspect`의 lint는 `.eslintcache`를 쓰므로 캐시 없이 따로 돌린다. 넷 다 소스를 수정하지 않는다.

```bash
pnpm type && pnpm exec eslint . --no-cache && pnpm test:scripts && pnpm test
```

이어서 `pnpm build`를 실행한다. `inspect`가 잡지 못하는 서버·클라이언트 경계 위반과 빌드 단계 오류를 여기서 본다. `.next`를 덮어쓰므로 같은 체크아웃에서 dev 서버가 돌고 있으면 실행하지 않고 그 사실을 기록한다. 빌드가 환경변수 부재로 실패하면 환경 문제로 분류한다.

실행 위치, 기준 커밋, 명령, 종료 코드, 실패 내용을 기록한다. 환경 문제로 실행하지 못하면 코드 문제와 구분하고 미검증 범위를 명시한다. 선행 실패로 일부 검증이 실행되지 않았다면 그 범위도 기록한다.

### 의존성 점검

부모 에이전트가 레포 루트에서 한 번 실행하고 결과를 「의존성」·「보안 취약점」 담당에 넘긴다. 둘 다 레지스트리에 접속하므로 네트워크가 없으면 환경 문제로 분류한다.

```bash
pnpm deps:check  # pnpm -r outdated
pnpm run audit   # pnpm audit --audit-level=high
```

`pnpm outdated`는 갱신할 패키지가 있으면 종료 코드 1을 돌려준다. `pnpm run audit`도 기준 이상 취약점이 있으면 1이다. 이것은 실패가 아니라 결과다. 실행 위치·명령·종료 코드·출력 요약을 기록하고 원문은 `.scratch/maintenance-audit/` 아래에 남긴다. 이번 단계에서 `pnpm deps:update`·`pnpm deps:update:major`·`pnpm audit --fix`를 실행하지 않는다.

## 결과 작성과 완료 조건

`docs/agents/issue-tracker.md` 규약에 맞춰 `.scratch/maintenance-audit/` 아래에 결과를 남긴다. 파일 구성은 다음과 같다.

| 파일                  | 내용                                                                                 |
| --------------------- | ------------------------------------------------------------------------------------ |
| `issues/NN-<slug>.md` | 확정된 문제를 한 건씩 기록                                                           |
| `report.md`           | 요약, 후보, 용어 비교, 조사 상태·파일 목록, 검증 결과·한계, 수정 묶음, 후속 프롬프트 |

새 조사라면 티켓은 `01`부터 번호를 매긴다. 각 티켓 상단에 `Status:` 라인을 두고 `docs/agents/triage-labels.md`의 라벨을 사용한다. 항목 ID는 티켓 번호 `NN`을 그대로 쓰며 `report.md`의 목록과 묶음에서 해당 티켓을 연결한다.

각 티켓에는 다음을 적는다.

- ID, 분류(P1·P2·P3), 파일·위치
- 관찰된 사실, 판단 근거, 영향, 권장 조치, 확신도
- 분류별 필요한 증거와 권장 조치의 검증 방법
- 테스트·주석 정리는 제거·통합·수정·보존 중 권장 대응과 근거

추가 확인이 필요한 후보는 `report.md`에만 기록한다. 티켓 번호는 부여하지 않고 ID를 미발급으로 표시한다. 제목으로 구분하고 티켓과 동일한 판단 정보에 확정에 필요한 확인 사항을 추가한다.

`report.md`에는 다음을 포함한다.

- 시작·종료 Git 상태, 기준 커밋, 조사 대상·제외 대상
- 다섯 영역별 상태와 파일별 직접 읽음·정적 검색·미점검 기록
- 확정된 문제 목록과 티켓 링크, 추가 확인 후보
- 용어 불일치 별도 목록: 개념, 정본 용어, 실제 표현, 위치, 필요한 명칭 차이 여부, 권장 대응, 관련 티켓 ID
- 원문 대조가 필요한 수치 목록. 대조를 마치면 `docs/fact-check-log.md`로 옮길 후보다
- 기존 문제와의 연결, 중복·오탐을 제외한 판단 근거
- 검증 명령과 결과, 환경 문제, 미실행·미조사 범위, 표본 조사의 한계
- `pnpm deps:check`·`pnpm run audit` 결과 요약, 갱신 후보를 patch·minor·major로 나눈 목록, 취약점 목록
- 외부 확인이 필요한 사항(야후 티커 생존, 외부 API 응답 형태, Vercel 헤더 기본값 등)
- 우선순위·의존성·변경 위험을 고려한 수정 묶음과 해당 티켓 번호

종료 전에 조사 결과 파일 외에 추적 파일이 변경되지 않았는지 시작 시점과 비교한다. 검증이 만든 비추적 산출물(`.next`, `.eslintcache`, `tsconfig.tsbuildinfo`)도 구분해 기록하고 기존 사용자 변경을 되돌리지 않는다.

완료 기준은 다섯 영역의 조사 상태와 파일별 범위가 기록되고, 확정된 문제의 근거·중복·오탐 검토가 끝나며, 검증 결과 또는 실행 불가 사유와 수정 묶음이 정리된 상태다. 미검증 범위를 숨기지 않는다.

아래 후속 수정 단계 프롬프트는 이번에 실행하지 않는다. 코드 블록의 내용을 `report.md` 끝에 원문 그대로 수록한다.

```text

- 조사 결과가 오탐이면 억지로 수정하지 말고 근거와 함께 정정해.
- 선택한 범위에 포함된 죽은 코드·테스트는 실제 소비처와 실행 경로를 재확인한 뒤 제거해.

- 선택한 범위의 쓸모없거나 오래된 주석과 주석 처리된 죽은 코드는 제거하거나 바로잡아. 주석에 적힌 건수·목록은 지금 코드에 맞춰.

- 제거 여부가 불확실하면 유지하고 추가 확인 사항을 기록해.
- 선택한 범위의 코드 이해 용이성 개선은 외부 동작과 화면 수치를 보존하면서 수행해. 추상화나 파일 분리가 이해 비용을 늘리면 도입하지 마.
- 래퍼·통과용 re-export·제네릭·팩토리는 선택한 티켓에서 제거 타당성이 확인된 후보만 인라인해. 호출처·인스턴스가 하나라는 사실만으로 제거하지 마. 규약이 정한 경계(use-*.ts의 useEndpoint 래퍼, use-chart.ts 재수출)와 단일 출처(ENDPOINTS·NAV_GROUPS·REGULATION·utils.ts 표기 함수)는 유지해.
- 라우트·ENDPOINTS·훅은 한 벌로 고쳐. 키를 읽는 라우트는 키가 없을 때 available: false를 돌려주게 해. 응답 모양을 바꾸면 캐시에 남은 옛 응답이 어떻게 읽히는지 적어.
- 수치를 고칠 때는 원문과 대조하고, 맞은 결과를 docs/fact-check-log.md에 남겨. 규제·세율 값은 기준과 함께 한 객체에 둬.
- 설정 파일은 실재하는 경로와 현재 도구 버전에 맞춰 고치고 효력 없는 설정은 지워. .env* 파일은 열지 마.

- 보안 취약점은 수정 버전으로 올리거나 overrides로 막아. 외부 확인이 필요한 건은 고치지 말고 후보로 남겨.
- shadcn primitive 교체는 선택한 티켓의 후보만 하고 기존 동작(포커스·키보드·aria)과 화면을 보존해. 맞는 variant가 없으면 소비처에서 덮지 말고 primitive 기본값이나 eslint.config.mjs의 no-restyle contract를 고쳐. src/components/ui/*를 바꾸면 ADR 0010의 재설치 시 재적용 목록도 갱신해. 새 primitive 추가는 티켓이 정한 것만 해.
- 수정 중 발견한 별개 문제는 issues/에 새 티켓으로 추가해.
- 변경 위험에 맞는 검증을 해. 화면에 영향을 주는 변경은 pnpm dev로 띄워 해당 페이지를 데스크탑·모바일 폭에서 확인하고, 확인하지 못한 범위와 이유를 명시해.
- 마지막에 레포 루트에서 pnpm inspect와 pnpm build를 실행해.
- 해결한 항목, 남은 항목, 제거·통합한 테스트와 보존한 검증, 주석 정리 내용, 코드 이해 용이성 개선 내용, 제거한 추상화, primitive로 교체한 자리, 고친 라우트·설정·수치, 갱신한 의존성과 막은 취약점, 검증 결과를 정리해.
- 커밋은 하지 마.
```
