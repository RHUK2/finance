# 비트코인 프로토콜 그룹 정비

`비트코인 프로토콜` 내비게이션 그룹 10개 페이지를 다섯 가지 축으로 정비한다: 설명 정정, 직관성, 페이지 간 일관성, 단순화, 중복 제거. `.scratch/bitcoin-insight/`에서 끝낸 인사이트 그룹 정비의 후속이며, 거기서 세운 규칙을 이어받는다.

## 섹션

| 섹션 | 대상                                                                     | 상태 |
| ---- | ------------------------------------------------------------------------ | ---- |
| S0   | 개념 인벤토리·중복 지도                                                  | 완료 |
| P1   | `/wallet-keys`, `/transactions`, `/script-verify`, `/multisig-timelock`  | 대기 |
| P2   | `/p2p-network`, `/block-mining`, `/chain-reorg`, `/soft-fork-activation` | 대기 |
| P3   | `/lightning-network`, `/privacy`                                         | 대기 |

P1이 가장 무겁다. `key-tree.tsx`가 28KB로 앱 전체에서 가장 큰 파일이고 `script-stack.tsx`가 14.7KB다. 그래도 네 페이지가 하나의 파이프라인(키 → 트랜잭션 → 스크립트 → 조건부 잠금)이라 쪼개지 않는다.

## 인사이트 그룹에서 이어받는 규칙

`.scratch/bitcoin-insight/spec.md`의 `껍데기·프리미티브 규칙` 표를 그대로 따른다. 이 그룹에서 달라지는 항목만 아래에 적는다.

| 항목                     | 프로토콜 그룹 규칙                                                                                                            | 인사이트와 다른 이유                                                                                                                    |
| ------------------------ | ----------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------- |
| 탭 번호 접두사           | 탭이 실제 순서를 가지면 `①②③`를 쓰고, 병렬 관점이면 쓰지 않는다                                                               | 프로토콜 탭 대부분이 파이프라인이거나 시간순이다. 인사이트에서 걷어낸 `illicit-funds` 세 탭은 순서가 아니라 세 각도였다                 |
| `IllustrativeDisclaimer` | 유지한다. 단 한 화면에 하나만 보이게 한다. 페이지 배너는 그 페이지 전체에 걸친 단순화만, 탭 배너는 그 탭 고유의 생략만 담는다 | 인사이트의 배너는 "이 숫자는 가짜다"였지만 여기는 "실제 프로토콜의 어느 부분을 생략했다"는 기술적 고지다. 오해하면 잘못된 지식을 얻는다 |
| 배너 문구 형식           | "실제로는 X인데 여기서는 Y로 줄였다"                                                                                          | 무엇을 생략했는지가 핵심이다                                                                                                            |
| 논쟁적 테제 라벨링       | 거의 적용되지 않는다                                                                                                          | 이 그룹은 명세다. 틀리면 그냥 틀린 것이고 논쟁의 여지가 없다                                                                            |
| 사실 검증                | 숫자·바이트 크기·BIP 번호·필드 이름은 전부 원문과 대조한다. 서술적 설명은 지식으로 판단한다                                   | 검증 대상이 BIP·Core 소스로 명확하다                                                                                                    |

## 구조 관찰

### 프리미티브 사용

`SectionIntro`와 `ExplainCard`는 10개 페이지 전부가 쓴다. `StatCard`는 그룹 전체에서 한 번도 쓰이지 않는다(인사이트의 `illicit-funds`만 쓴다). `AgentGrid`·`Sparkline`도 쓰이지 않는다. 캐스케이드형 시뮬레이션이 없으니 자연스럽다.

`Pipeline`(`src/components/pipeline.tsx`)은 이 그룹 전용 프리미티브로 `wallet-keys`·`transactions`·`script-verify`·`block-mining`이 쓴다.

### 모델 배치

프로토콜 그룹은 모델을 `src/lib/<domain>-concept.ts`에 둔다. 인사이트 그룹은 `src/app/<page>/models.ts`에 둔다. `CLAUDE.md`의 아키텍처 절에는 `bitcoin-models.ts`만 적혀 있고 `*-concept.ts` 규약은 없다.

"여러 페이지가 공유하면 `lib/`"이라는 기준을 세울 수 있는지 실제 참조 관계를 확인했다.

| 파일                | 쓰는 페이지                                  | 공유되는가 |
| ------------------- | -------------------------------------------- | ---------- |
| `tx-concept`        | transactions, p2p-network, lightning-network | 그렇다     |
| `script-concept`    | script-verify, multisig-timelock             | 그렇다     |
| `block-concept`     | block-mining                                 | 아니다     |
| `chain-concept`     | chain-reorg                                  | 아니다     |
| `bip-concept`       | wallet-keys                                  | 아니다     |
| `p2p-concept`       | p2p-network                                  | 아니다     |
| `privacy-concept`   | privacy                                      | 아니다     |
| `lightning-concept` | lightning-network                            | 아니다     |
| `soft-fork-concept` | soft-fork-activation                         | 아니다     |

9개 중 7개가 한 페이지 전용이다. 공유 여부로 배치가 갈린 게 아니라 그룹의 관례일 뿐이다. 파일을 옮기는 리팩터는 범위 밖으로 두되, `CLAUDE.md`에는 기준이 아니라 사실대로 적는다.

## 중복 지도

### D1. 주소 타입 정의가 두 곳에 있다 (심각, P1에서 해결)

같은 세 주소 타입을 두 lib 파일이 각자 테이블로 들고 있다.

|              | `tx-concept.ADDR_TYPES`             | `script-concept.SCRIPT_ADDR_TYPES`   |
| ------------ | ----------------------------------- | ------------------------------------ |
| 타입 수      | 4 (legacy, nested, native, taproot) | 3 (nested 없음)                      |
| 담는 값      | `purpose`, `inputVb`, `outputVb`    | `sigAlgo`, `unlockField`, `sigBytes` |
| taproot 라벨 | `Taproot (P2TR)`                    | `Taproot (P2TR, key-path)`           |
| 조회 함수    | `addrMeta`                          | `addrMeta`                           |

문제가 셋이다. 첫째, 두 파일이 같은 이름 `addrMeta`를 export해 한 파일에서 둘 다 쓰려면 별칭이 필요하다. 둘째, Nested SegWit이 한쪽에만 있어 독자가 `트랜잭션 해부`에서 본 타입이 `스크립트·서명 검증`에서 사라진다. 셋째, 라벨 문자열이 부분적으로만 일치해 같은 것을 가리키는지 코드에서 보장되지 않는다.

주인: 주소 타입의 정체(값·라벨·purpose)는 한 곳에서 정의하고, 수수료 정보와 서명 정보는 각자 덧붙이는 구조로 간다.

### D2. 최장 체인 규칙 (중간)

| 위치                                | 관점                                                                   |
| ----------------------------------- | ---------------------------------------------------------------------- |
| `block-mining/difficulty-consensus` | 정본. "가장 긴"이 아니라 "누적 작업량이 가장 많은"이라는 정정까지 포함 |
| `p2p-network/ibd-sync`              | 헤더만으로 그 판정이 가능한 이유                                       |
| `chain-reorg/attack-scope`          | 과반 공격자도 누적 작업량은 다시 못 해낸다                             |

관점이 갈리므로 셋 다 남긴다. 주인은 `block-mining`이고 나머지 둘이 링크한다.

### D3. 51% 공격 (중간, 확인 결과 이미 해결돼 있었음)

인사이트 그룹 정비 때 `bitcoin-game-theory/attack-game`에서 `/chain-reorg`로 가는 링크를 넣었지만 역방향이 없다. `chain-reorg`만 읽은 독자는 "왜 아무도 안 하는가"라는 경제적 답을 못 얻는다.

주인: 기술은 `/chain-reorg`, 경제는 `/bitcoin-game-theory`.

P2에서 확인하니 역방향 링크가 이미 `attack-scope`의 `과반 공격자도 할 수 없는 것` 카드 안에 있었다. S0에서 브라우저로 링크를 셀 때 ① 탭만 마운트된 상태여서 못 봤다. 티켓 03 참조.

### D4. 수수료 (중간)

`transactions/fee-calc`(크기가 수수료다), `transactions/address-compare`(주소 타입별), `p2p-network/mempool-policy`(최소 릴레이 수수료·RBF), `mempool` 대시보드(실시간 권장 수수료). 층위가 다르므로 서술 중복은 없다. 링크만 검토한다.

### D5. 타임락 (낮음)

`multisig-timelock/timelock-lab`이 CLTV·CSV 정본이고, `lightning-network/htlc-routing`이 HTLC 안에서 그것을 쓴다. 링크한다.

### D6. 체인분석 (낮음)

`privacy/chain-analysis`와 인사이트 그룹 `illicit-funds/laundering-trail`이 같은 휴리스틱을 다루지만 이미 상호 링크되어 있다. 손대지 않는다.

### D7. p2p-network 고지문이 자기 구현과 모순된다 (심각)

페이지 최상단 배너는 "전파 그래프는 실제 무작위 P2P 그래프 대신 격자로 근사했다"고 말한다. 그런데 `lib/p2p-concept.ts`의 `generateGossipGraph`는 무작위 스패닝 트리에 무작위 간선을 더한 무작위 그래프를 만들고, 같은 파일 주석은 "그래프가 격자가 아니라 무작위라는 점은 실제와 같은 구조로 재현한다"고 정반대로 쓴다. 탭 안의 배너도 "격자보다 훨씬 적은 홉 수로 퍼지는 걸"이라며 격자와 대비한다.

페이지 배너가 옛 구현을 설명한 채 남았다. 독자가 처음 보는 문장이 시뮬레이션을 실제보다 부실하게 소개하고 있다.

### D8. 번호 체계가 중첩된다 (낮음)

`p2p-network/mempool-policy`는 탭 라벨이 `② 멤풀 수용 정책`인데, 그 안에서 `SectionIntro`가 다시 `① 신규 트랜잭션 수용 판정`, `② RBF`로 번호를 매긴다. 한 화면에 두 층의 번호가 겹친다.

## 용어집 계획

`CONTEXT.md`는 인사이트 그룹 정비에서 `공통` / `채택 게임` / `홀더 게임` / `권력 투사` / `체제 전환` / `전력망` / `자금 추적` 일곱 절이 됐다. 프로토콜 그룹은 개념 밀도가 훨씬 높지만, 대부분은 비트코인 표준 용어(UTXO, scriptPubKey, witness, nonce, CLTV 등)라 이 프로젝트가 고유하게 정하는 말이 아니다.

용어집은 프로젝트가 여러 표현 중 하나를 고를 때 쓰는 것이므로, 표준 용어를 그대로 옮겨 적지 않는다. 실제로 흔들리는 것만 넣는다. P2에서 `## 체인 확정` 절(확인 수·누적 작업량·재구성·임계값)을 추가했다. S0 시점에 후보로 본 것은 다음이다.

- 주소 타입 이름표: `Legacy (P2PKH)` / `Native SegWit (P2WPKH)` / `Taproot (P2TR)`를 어느 표기로 통일할 것인가 (티켓 01과 직결)
- `확인 수` vs `컨펌`
- `누적 작업량` vs `최장 체인` (`block-mining`이 이미 후자를 부정확하다고 정정하고 있다)
- `홉`: 인사이트 그룹 자금 추적 절에 이미 정의돼 있는데, `p2p-network`의 전파 홉은 다른 뜻이다. 충돌 확인 필요

각 섹션에서 실제로 흔들리는 것이 확인될 때만 절을 만든다.
